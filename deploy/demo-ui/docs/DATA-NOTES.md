### 2.2 路网生成算法
1. **构造"线"集合**（尚未拓扑化）：内环 + 外环（expressway）、8 条放射干道（arterial）、5 条区界道路、粗网格（130 世界单位 = 650 m）、细网格（65 单位 = 325 m，仅 `r < 640`）、6 条行政区边界环路。
2. **平面细分（planar subdivision）**：把全部线段放进 90 单位的空间哈希，两两求交得到切分参数，按参数切段，再做**端点焊接**（坐标量化到 0.5 世界单位 = 2.5 m）。
3. **去重与碎段清理**：同节点对只保留一条边；丢弃短于 1.0 世界单位（5 m）的碎段。
   > 这个阈值刻意取得很小 —— 早期用 11 m 会把环路在中间打断，导致走廊拼链只剩一小段。
4. **悬挂末端剪枝**：反复删除"端点为度 1 且长度 < 55 单位"的边（最多 6 轮），把噪声支路清掉。
5. **组装**：`roads` / `intersections` / `graph`（无向邻接，`oneway` 只保留正向）。

### 2.3 行政区几何
- **中心城区**：半径 240 世界单位的正圆盘，每 3° 一点。
- **外围 5 区**：围绕中心圆盘的 5 个 72° 环形扇区。相邻区**共用同一条径向分界线**（`borderWobble` 是纯函数，且会把角度**先归一化到 [0,360)** —— 东区的 `a1=396` 与南区的 `a0=36` 是同一条界，不归一化 hash 会得到两条几乎重合的平行道路）。
- `district.polygon` 是契约要求的 **`[[x,z], ...]` 数组形态**；另存 `_polyPts`（`{x,z}` 形态）供内部几何计算复用。
  > 这个坑很隐蔽：`U.pointInPolygon/Area/Centroid` 只认数组形态，早期给的是对象形态，导致**所有路段都被归到"中心城区"且面积为 NaN**。

### 2.4 建筑
- 系统化扫描行政区包围盒（格位 12 单位 = 60 m，打散访问顺序避免上限截断偏向一角）。
- 逐个校验：落在区内 / 不在水系 / 不在绿地 / **与最近道路的垂距 ≥ `max(w,d)/2 + 退让`**（中心城区退让 3 单位 = 15 m，外围 5 单位 = 25 m，符合 CBD 贴线建设的实际）。
- 高度 = 区基准高度 × 距中心衰减 × fBm 噪声，再按类型封顶（住宅 ≤62、工业 ≤34、商业 ≤74）。
- 每区把最高的 1~3 栋升级为 `landmark`（高度 ×1.55）并命名。
- 格位尺寸是被实测逼出来的：早期用 24 单位只能落到目标的一半 —— 路网退让后可用缝隙不够塞。

### 2.5 信号与走廊
- 信号只设在**该设的地方**：含快速路的节点是立交（不设）、纯支路交叉口不设、至少要有主干路或次干路参与且 `degree >= 3`。
  > 修正前有 28% 的信号机长在快速路上、46% 长在纯支路四岔口，明显不合理。
- 走廊 = 按 `等级 + 路名` 分组的同名道路链（贪心游走拼接），取总里程最长的 8 条。
- 走廊信号序列改成**投影到走廊折线求弧长后排序**（`corridorSignals`）。
  > 早期按采样点找最近信号机，顺序会回跳，实测绿波相位差出现 +5 s 的异常跳变；现在 23 站距离严格单调。
- 快速路走廊（C01 外环高速、C02 内环快速路）**不参与绿波**，信号数为 0。

## 3. 交通模拟引擎 `TP.Sim`

### 3.1 核心设计：闭式函数
路况是 `f(路段固有属性, 时刻, 潮汐方向)` 的**闭式函数**，不是逐帧累加的状态机。
- 因此同一 minute 反复 `setTime` 结果**逐字段完全一致**（自测断言 1792 条路段 × 10 个字段拼接串相等），时间轴可任意来回擦洗。
- 对象池：`roadStates` / `districtStats` / `signalStates` / `parkingState` / `bikeState` 在 `init` 时一次性创建，`setTime` **只改字段值不 new 对象**（自测断言引用不变）。

### 3.2 需求曲线
工作日 = 夜间底 0.095 + 早高峰 `N(495,55)×0.95` + 晚高峰 `N(1080,78)×1.00` + 午间 `N(735,62)×0.62` + 晚间 `N(1260,90)×0.22`。
周末 = 夜间底 0.180 + 上午肩峰 `N(660,90)×0.32` + 单主峰 `N(900,165)×0.80` + 晚间 `N(1170,95)×0.40`。

> 周末主峰与晚间肩峰在 17:00~18:00 会**叠加**，只看主峰中心会误判峰值偏低 —— 这是调参时踩过的坑。

### 3.3 关键实测（拥堵指数 0~10，>6 为拥堵）
| 指标 | 实测 |
|---|---|
| 早高峰峰值 | **08:15 = 4.52** |
| 晚高峰峰值 | **18:05 = 5.46**（高于早高峰，更宽） |
| 午间小凸起 | 12:15 = 1.21 |
| 凌晨谷底 | 最高 0.40 |
| 全网均速 | 晚高峰 28.4 km/h vs 凌晨 49.9 km/h |
| 晚高峰等级分布 | 畅通 505 / 缓行 504 / 拥堵 375 / 严重 408（**43.7% 拥堵以上**） |
| 早高峰潮汐 | 进城饱和度 0.945 vs 出城 0.641 |
| 晚高峰潮汐 | 出城饱和度 1.055 vs 进城 0.719 |
| 周末峰值 | 14:55 = 3.95（< 工作日 5.46） |

### 3.4 速度—饱和度阻抗
`speedRatio = 1 / (1 + 1.15 · sat^4.2)`（BPR 型）
- sat 1.0 → 0.465（拥堵）｜sat 1.2 → 0.288（严重拥堵）｜sat 0.5 → 0.94（畅通）
- 拥堵指数 `CI = clamp(12 · (1 - speedRatio)^1.1, 0.4, 10)`

### 3.5 事件
- 事件池 78 条，`since` 用**需求曲线的逆 CDF 采样**，因此高峰时段事件自然更密集。
- 每条事件预计算**受影响路段表**（`affected[{i,w}]`，60 单位内权重 1.0，240 单位内线性衰减到 0.18）。
- 实测：任意时刻均值 5.0 起、峰值 15 起；受事件影响路段 **1997/1997 全部被降速**。

### 3.6 绿波
- 相位差 `offset = (沿走廊弧长 / 推荐车速) mod 周期`，弧长取自 `corridor.signalArcs`（city-model 记录），比相邻站点直线距离更准（弯道走廊用直线会系统性低估行程时间）。
- 实测：春熙路走廊 23 站、推荐车速 45 km/h、带宽 24 s、效率 0.763；6 组绿波（2 条快速路不参与）。

### 3.7 公共交通运能口径（**踩过单位坑**）
`dailyRidership` / `ridership` 是**万人次**，`capacityHour` / `vehicleCapacity` 是**人次**。混用会让满载率恒等于下限 0.02。
- 运能由「高峰小时客流 ÷ 设计满载 0.92」反推：`capacityHour = daily × 0.095 × 10000 / (0.92 × capFactor)`，`capFactor ∈ [0.86, 1.14]` 给线路间制造差异。
- 发车频率自洽：`vph = max(minVph, 高峰小时人次 / 单车定员)`，`headwayActual = 60 / vph`。
- 实测：高峰地铁满载率 **1.03** vs 平峰 0.087；高峰公交准点率 84.5% vs 平峰 93.5%。

## 4. 数据接口门面 `TP.Api`

前端（图表层与 UI 层）的**唯一取数入口**。3D 图层因为每帧要读上千条路段，允许直读 `TP.Sim`；其余一律走这里。

### 4.1 设计要点
- **纯函数 + 缓存**：所有派生数据按 `(minute, dayType, regionId, moduleId, signalGroupId, 额外键)` 做签名缓存，状态一变即失效。
- **不持有业务状态**：只持有 UI 交互状态 `state`（时间/日型/行政区/视角/模块/图层/选中/信号组/指标）。
- **事件总线**：`'ready' 'time' 'daytype' 'region' 'view' 'module' 'layer' 'select' 'signalgroup' 'metric' 'live'`，`on()` 返回取消订阅函数。
- **后端适配器**：`TP.Api.adapter` 提供 `mode: 'mock'|'live'` / `baseUrl` / `fetchSnapshot()` / `pushSelect()`。
  切真实后端只需把 `mode` 设为 `'live'` 并配 `baseUrl`，前端零改动。`fetch` 不存在或 `file://` 下会安全降级返回 `null`。

### 4.2 就绪判断（易踩）
```js
TP.Api.ready()   // → boolean（是函数）
TP.Api.isReady   // → boolean（getter）
```
⚠️ **不要写 `if (TP.Api.ready)`** —— 函数永远是真值，会绕过就绪检查。短路判断请用 `isReady`。

### 4.3 默认时刻
`TP.Api.init()` 会把 `state.minute` 设为**真实时间的分钟数**；若落在深夜（<06:00 或 >23:00），改为 **08:10** —— 否则评审一打开就是"空城"。可用 `setMinute()` 随时改。

### 4.4 图层 id（与 `docs/3D-CONTRACT.md` §5.1 必须逐字一致）
```
traffic vehicle heat incident metro bus od signal parking bike carbon district
```
默认开启：`traffic` / `heat` / `incident` / `district`。

## 5. 已知简化与不足

1. **路网是"路段级"而非"车道级"**：`roads[]` 是相邻交叉口之间的一段，同名道路会拆成多条共享 `name` 的条目（如"中山大道"有 20+ 段）。没有车道级渠化、没有转向禁限。
2. **河流与道路不做立交建模**：水系在 y = −0.4 渲染，道路在其上方，视觉上读作"桥"，但没有真实的桥隧结构。
3. **土地用途是基于行政区性格的统计性分配**，不是真实的用地规划；因此建筑形态"像"而不是"对"。
4. **`districtId` 判定用"点是否落在多边形内 + 最近中心兜底"**：实测 96.3% 的路段首点确实落在其所属区内，剩余 3.7% 是多边形边界附近的抖动（路段跨越区界时只按首点归属）。这是刻意的简化：真实系统按路段中点或重叠区处理。
5. **信号配时是统计生成**：周期 90~160 s、各进口道绿信比均分（含 ±1 s 余数分配），不是真实配时方案；"自适应"仅表现为高峰周期微调 +16 s。
6. **OD 是重力模型 + 真实路网最短路**：`T_ij ∝ w_i·w_j·exp(−d/9.5)`，不是从手机信令反推的真实 OD。
7. **`forecast` 是"确定性曲线 + 展宽置信带"**，不是统计预测模型。置信带宽度按 `band × (0.35 + 1.75·h)` 线性展宽，仅用于视觉表达不确定性。
8. **周一至周日不做区分**，只区分工作日/周末；无节假日、无天气耦合（"恶劣天气"事件是事件池里的类型，不改变全局需求曲线）。
9. **`roadTimeline` 有 40 条路的 LRU 缓存**：用户连点上百条路段详情不会撑爆内存，但超出后最早的那条会被淘汰重算。

## 6. 给下游的联调提示

- 数据层已冻结，**接口签名不会再变**。如需新字段请在 `docs/APP-CONTRACT.md` 上讨论后再加。
- 若要排查"3D 颜色不对"，先确认读的是 `roadStates[id].level`（0~3）或 `.speedRatio`，而不是 `.congestionIndex`（那是 0~10 的指数，只用于排行与详情）。
- 若要排查"图表没数据"，先确认 `TP.Api.isReady` 为真 —— `index.html` 里 `js/data/data-api.js` 的 script 标签必须存在且排在 `sim-engine.js` 之后。
- 时间轴热力条的档位（`data-level` 1~4）取自**拥堵指数**分档（<2.5 / <5 / <7.2 / ≥7.2），不是速度比 —— 全网均速是平均值，再堵也跌不到自由流的 30%，用速度比会让热力条永远只有两档。
